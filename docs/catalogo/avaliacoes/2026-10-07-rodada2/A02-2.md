## Saída bruta

Virtual threads ajudam a atender muitas requisições I/O-bound sem esgotar threads de plataforma, mas não aumentam a capacidade do banco: o limite continua sendo 10 conexões. Eu usaria virtual threads junto com admissão limitada para que no máximo 10 operações deste serviço usem o banco ao mesmo tempo; o excedente aguardaria por um prazo curto ou receberia resposta de sobrecarga.

Assumo Java 25 com Spring Boot 4 e que as 10 conexões estejam reservadas para esta aplicação. Se houver mais de uma réplica ou outros consumidores do banco, o orçamento por instância precisa ser reduzido para que a soma de todos os pools e jobs permaneça dentro das 10 conexões.

Ativaria virtual threads e configuraria o HikariCP com limite e espera finita:

```yaml
spring:
  threads:
    virtual:
      enabled: true
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 10
      connection-timeout: 2000 # ms; timeout deve caber no deadline da requisição
```

Também colocaria um semáforo singleton compartilhado por todos os caminhos que usam esse banco. A admissão deve ocorrer antes de entrar no método transacional; assim, a espera pelo semáforo não mantém uma transação/conexão aberta. Uma espera limitada e rejeição explícita evita acumular uma fila invisível de virtual threads:

```java
@Component
public class AdmissaoBanco {
    private final Semaphore permissoes = new Semaphore(10);

    public <T> T executar(Supplier<T> operacao) {
        boolean adquirida = false;
        try {
            adquirida = permissoes.tryAcquire(200, TimeUnit.MILLISECONDS);
            if (!adquirida) {
                throw new BancoSaturadoException(); // traduzir para HTTP 503
            }
            return operacao.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new BancoSaturadoException(e);
        } finally {
            if (adquirida) {
                permissoes.release();
            }
        }
    }
}
```

O chamador envolve a chamada ao bean transacional com `admissaoBanco.executar(() -> casoDeUsoTransacional.executar(...))`. O semáforo deve cobrir apenas o trabalho de banco e liberar a permissão em sucesso ou falha. Transações devem ser curtas; não mantenha conexão durante chamadas HTTP ou backoff. Se o serviço possuir fluxos com prioridades diferentes, reserve capacidade ou use pools separados com orçamento explícito.

Eu observaria conexões ativas/ociosas/pendentes, tempo e timeout de aquisição, rejeições e duração das transações. Validaria que o máximo de operações simultâneas no banco nunca passa do orçamento, que falhas liberam a permissão e que o excedente é rejeitado no prazo definido. A configuração real depende do total de réplicas e do orçamento compartilhado do banco.
