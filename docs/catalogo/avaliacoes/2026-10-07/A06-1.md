## Saída bruta

**Variante inferida:** `k8s` (probes e health groups). Não alterei nenhum arquivo.

### Não vou fazer isso: liveness não deve falhar por dependência fora

Fazer a liveness falhar em todos os pods quando uma dependência cai (banco, broker, cache, API externa) transforma uma indisponibilidade parcial em **reinício em massa**. Pelo padrão do catálogo, falha de liveness faz o kubelet reiniciar o container. Se o banco cai:

1. Todos os pods falham a liveness quase ao mesmo tempo e são reiniciados juntos.
2. A aplicação inteira fica fora, em vez de só degradada.
3. Quando a dependência volta, todos os pods sobem de uma vez (JVM fria, pools abrindo conexões em paralelo), o que pode derrubar a dependência de novo.
4. O reinício não conserta nada, porque o problema está fora do processo.

A semântica do catálogo é esta:

| Probe | Pergunta | Inclui | Nunca inclui | Falha causa |
|---|---|---|---|---|
| startup | Terminou de subir? | estado de inicialização | - | Espera, sem reiniciar cedo |
| liveness | O processo está são? | `livenessState` | Banco, broker, cache, APIs externas | Reinício do container |
| readiness | Esta réplica pode atender agora? | `readinessState` + dependências necessárias | Dependências opcionais; métricas de carga | Sai do balanceador, sem reinício |

### O que fazer quando a dependência cai: a readiness é que deve falhar

O efeito desejado ("pods param de receber tráfego quando a dependência está fora") vem da **readiness**, que tira a réplica do Service sem reiniciar. Configuração correta:

```yaml
# application.yaml
management:
  endpoint:
    health:
      probes:
        enabled: true
      group:
        liveness:
          include: livenessState          # só o processo
        readiness:
          include: readinessState, db     # dependências necessárias para atender
```

```yaml
# Deployment (trecho)
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 24
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 15
  failureThreshold: 3
```

Resultado esperado com o banco fora: liveness 200 (sem reinício), readiness 503 (pods saem do balanceador), e voltam sozinhos quando o banco volta. Se a dependência for opcional/degradável, ela nem entra na readiness.

### Se o objetivo é testar o comportamento

Se a intenção era **simular** a queda para ver como o sistema reage, faça isso com um experimento de falha controlado (ex.: toxiproxy entre app e dependência; ver `skills/chaos-engineer/references/toxiproxy-java.md`, agent `engenheiro-chaos`), validando que a readiness cai e a liveness continua verde. Para alertar sobre isso, use alerta sobre readiness/ausência de endpoints (agent `especialista-monitoramento`).

### Se há um motivo real para reiniciar

Se o processo está travado de verdade (deadlock, thread pool esgotado de forma irrecuperável), a liveness pode refletir isso por um indicador **do próprio processo**, nunca por dependência externa. Me diga o cenário e ajusto.

## Pontuação
- Itens obrigatórios:
  - ✅ Liveness não depende de serviço externo: "liveness | ... | Nunca inclui | Banco, broker, cache, APIs externas"; recusa o pedido.
  - ✅ Readiness só com dependência necessária: "`include: readinessState, db` # dependências necessárias para atender".
  - ❌ Degradação explícita: só aparece "Se a dependência for opcional/degradável, ela nem entra na readiness". Não define o que a aplicação faz com a dependência fora (falha rápida com 503/Problem Details, fallback, rotas parciais). Também não percebe que `db` na readiness de **todas** as réplicas esvazia o Service.
  - ✅ Forma de verificar: "`kubectl apply --dry-run=client` e teste com banco fora (liveness 200 / readiness 503)".
- Falha bloqueadora: não
- Justificativa: a semântica das probes está correta e há validação, mas a degradação é só mencionada, sem decisão, o que limita a nota a 1.
