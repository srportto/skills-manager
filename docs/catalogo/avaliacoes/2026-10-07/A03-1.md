## Saída bruta

### Escopo e hipóteses (não vou perguntar; declaro e sigo)

O pedido é adicionar a uma aplicação hexagonal existente a repetição de uma cobrança quando a resposta do gateway de pagamento estoura o timeout. Hipóteses assumidas:

- Há um gateway de pagamento remoto (HTTP) atrás de uma `port/out`. O gateway aceita uma **chave de idempotência** no pedido e permite **consultar a cobrança por essa chave**. Se ele não oferecer nenhuma das duas coisas, a repetição automática **não é segura** e eu não implementaria o retry. Nesse caso o fluxo vira "marcar `PENDENTE_RECONCILIACAO` e reconciliar por outro canal".
- Deadline total de 2 s para a operação lógica do cliente. Até 3 tentativas, com a chamada inicial contando como uma. Backoff exponencial com base de 50 ms, teto de 200 ms e full jitter. Timeout de I/O de 600 ms por tentativa, derivado do orçamento restante.
- Esta camada (o serviço) é a única dona do retry. Cliente HTTP, SDK e gateway da borda ficam com retry automático desligado. Senão três camadas com três tentativas dão 27 chamadas.
- Java 25, Spring Boot 4, base hexagonal `domain`/`application`/`infrastructure`. O pacote usado abaixo é `br.com.srportto.cobranca`.

### Decisão central

Timeout de resposta **não é rollback remoto**: a cobrança pode ter sido efetivada. Repetir "às cegas" cobra em dobro. Por isso o fluxo é:

1. Gera a chave de idempotência **uma vez** por cobrança lógica e a persiste junto com o payload (estado `EM_ANDAMENTO`).
2. Tenta cobrar com essa chave, sempre a mesma.
3. Se der timeout, o resultado é **desconhecido**. Antes de repetir, **consulta** o gateway pela chave:
   - existe e aprovada: assume o resultado, sem nova cobrança;
   - existe e recusada: erro de negócio, sem repetição;
   - não existe: repete com a mesma chave. Se o gateway ainda assim processar as duas, a chave garante efeito único.
4. Só **timeout e falha de I/O** são elegíveis a retry. Recusa de cartão, payload inválido, cancelamento e interrupção nunca são repetidos.
5. Esgotou tentativas, quota ou deadline: o estado vira `PENDENTE_RECONCILIACAO`. O sistema **não inventa sucesso nem falha**. Um job de reconciliação, fora do escopo deste pedido, consulta pela chave.

Alternativa rejeitada: repetir direto, sem consulta. É mais simples, mas depende de o gateway deduplicar corretamente e deixa a decisão invisível. A consulta custa uma chamada a mais e dá evidência. Também rejeitei circuit breaker e bulkhead agora: não há medição de tráfego que os justifique (proporcionalidade). O ponto de extensão fica na porta.

public record ChaveIdempotencia(String valor) {

```java
// application/usecase/CobrarService.java
public class CobrarService implements CobrarUseCase {

    private static final int MAX_TENTATIVAS = 3;
    private static final Duration TIMEOUT_POR_TENTATIVA = Duration.ofMillis(600);
    private static final Duration BASE_BACKOFF = Duration.ofMillis(50);
    private static final Duration TETO_BACKOFF = Duration.ofMillis(200);

    private final GatewayPagamento gateway;
    private final RegistroCobranca registro;      // port/out: persiste chave + payload + estado
    private final Clock relogioMonotonico;        // injetável para o teste
    private final Esperador esperador;            // injetável: nenhum Thread.sleep no teste
    private final DoubleSupplier jitter;          // [0,1), injetável

    @Override
    public ResultadoCobranca cobrar(Cobranca cobranca, Duration deadlineTotal) {
        // Chave e payload gravados ANTES da primeira chamada: reinício do processo reaproveita a chave.
        var chave = registro.obterOuCriar(cobranca.idPedido(), ChaveIdempotencia::nova, cobranca);
        var orcamento = OrcamentoTempo.iniciar(deadlineTotal, relogioMonotonico);
        long atrasoMaximo = BASE_BACKOFF.toNanos();

        for (int tentativa = 1; tentativa <= MAX_TENTATIVAS; tentativa++) {
            if (orcamento.esgotado()) break;                       // não inicia I/O sem tempo
            try {
                var resultado = gateway.cobrar(chave, cobranca, timeoutDaTentativa(orcamento));
                return registro.concluir(chave, resultado);
            } catch (TimeoutRespostaException desconhecido) {
                // Efeito desconhecido: reconcilia ANTES de repetir.
                var jaEfetivada = gateway.consultar(chave, timeoutDaTentativa(orcamento));
                if (jaEfetivada.isPresent()) {
                    return registro.concluir(chave, jaEfetivada.get());
                }
                if (tentativa == MAX_TENTATIVAS) break;
                atrasoMaximo = aguardarBackoff(atrasoMaximo, orcamento); // false => sem tempo, encerra
                if (atrasoMaximo < 0) break;
            }
            // RecusaNegocioException e demais erros NÃO são capturados: não são repetidos.
        }
        return registro.marcarPendente(chave);   // PendenteReconciliacao; nunca inventa sucesso
    }

    private Duration timeoutDaTentativa(OrcamentoTempo orcamento) {
        // Nunca maior que o restante do orçamento (menos margem).
        return TIMEOUT_POR_TENTATIVA.compareTo(orcamento.restante()) < 0
                ? TIMEOUT_POR_TENTATIVA : orcamento.restante();
    }

    // Retorna o próximo teto de backoff, ou -1 se a espera consumiria o deadline (encerra antes de dormir).
    private long aguardarBackoff(long atrasoMaximo, OrcamentoTempo orcamento) {
        var atraso = Duration.ofNanos((long) (atrasoMaximo * jitter.getAsDouble())); // full jitter
        if (atraso.compareTo(orcamento.restante()) >= 0) return -1;
        esperador.aguardar(atraso);   // sem segurar conexão nem permissão durante a espera
        return Math.min(TETO_BACKOFF.toNanos(), atrasoMaximo * 2);
    }
}
```

var requisicao = HttpRequest.newBuilder(uri)
        .timeout(timeout)
        .header("Idempotency-Key", chave.valor())      // a mesma chave em todas as tentativas
        .POST(BodyPublishers.ofString(json))

try {
    var resposta = http.send(requisicao, BodyHandlers.ofString());
    return traduzir(resposta);                          // 4xx de negócio => Recusada, 5xx => erro técnico
} catch (HttpTimeoutException e) {
    throw new TimeoutRespostaException(e);              // resultado desconhecido, elegível à reconciliação
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();                 // interrupção respeitada, não vira retry

### Provas (escritas antes da implementação; devem falhar primeiro)

Relógio e espera injetados, valores literais, nenhum `sleep`. Cada teste detecta um defeito observável.

| Defeito detectado | Teste | Asserção principal |
|---|---|---|
| Cobrança em dobro após timeout | `naoDeveCobrarDeNovoQuandoConsultaMostraCobrancaAprovada` | `cobrar` chamado 1 vez; resultado `Aprovada`; `consultar` chamado 1 vez |
| Retry sem a mesma chave | `deveRepetirComAMesmaChaveQuandoGatewayNaoRecebeu` | as 2 chamadas de `cobrar` recebem chave igual |
| Repetir erro de negócio | `naoDeveRepetirQuandoCartaoRecusado` | 1 tentativa; `Recusada`; zero esperas |
| Retry infinito ou sem teto | `deveParar​AposTresTentativasEMarcarPendente` | 3 chamadas; `PendenteReconciliacao`; esperas literais `[5ms, 10ms]` com jitter 0,5 |
| Dormir além do deadline | `naoDeveDormirQuandoEsperaConsomeODeadline` | encerra pendente sem registrar espera |
| Timeout maior que o restante | `timeoutDaTentativaNaoPassaDoOrcamentoRestante` | argumento `timeout` recebido pelo fake <= restante |
| Interrupção convertida em retry | `interrupcaoNaoDeveVirarRetry` | flag de interrupção restaurado; 1 tentativa |
| Reinício perde a chave | `reinicioDeveReaproveitarAChaveRegistrada` | mesmo `registro` real (H2), segunda instância usa a chave gravada |
| Duas requisições concorrentes do mesmo pedido | `duasRequisicoesConcorrentesNaoDevemCobrarDuasVezes` | `CyclicBarrier` + chave única no banco; 1 efeito |

### Limites implementados

| Limite | Valor | Unidade e escopo | Motivo |
|---|---|---|---|
| Tentativas | 3 | por cobrança lógica, incluindo a inicial | evitar amplificação |
| Deadline | 2 s | por requisição lógica | prazo do cliente |
| Timeout de I/O | 600 ms | por tentativa, limitado ao restante | não reter conexão |
| Backoff | 50 ms a 200 ms, full jitter | entre tentativas | evitar sincronização de retries |
| Elegibilidade | só timeout e I/O | por tipo de erro | recusa e payload inválido são permanentes |

Rejeição ou pendência: `PendenteReconciliacao` com métrica `cobranca_pendente_total` (contador) e log com `traceId` e chave. O job de reconciliação fica como **pendência** a combinar. Ele pode ser desenhado com `especialista-monitoramento` para o alerta.

### Pendências e encaminhamentos

- **Confirmar com o gateway** que existem `Idempotency-Key` e consulta por chave. Sem isso, o retry automático não deve ir para produção.
- Tabela e port de `RegistroCobranca` (chave com índice único por pedido, estado, payload): detalhes de persistência em `persistencia-jpa`. Gravar estado e chave na mesma transação.
- Job de reconciliação de pendentes e alertas: `especialista-monitoramento` e/ou `arquiteto-sistemas`.
- Antes de declarar pronto, a entrega passa por `java-revisor` em modo `auditoria` (obrigatório). Em especial: retry em uma única camada, ausência de fallback que invente sucesso e liberação de recursos antes do backoff.

## Pontuação
- Itens obrigatórios:
  - ✅ Resultado desconhecido: "Timeout de resposta **não é rollback remoto** ... o resultado é **desconhecido**".
  - ✅ Chave idempotente persistida no provedor e localmente: "Gera a chave ... **uma vez** ... e a persiste junto com o payload", e o header `Idempotency-Key` com "a mesma chave em todas as tentativas".
  - ✅ Consultar ou reconciliar antes de repetir: "Antes de repetir, **consulta** o gateway pela chave"; esgotado o limite, o estado vira `PENDENTE_RECONCILIACAO`.
  - ✅ Limites e prova: 3 tentativas, deadline de 2 s, timeout derivado do restante (`timeoutDaTentativa`), tabela de testes com o defeito que cada um detecta, mutação e comandos.
- Falha bloqueadora: não
- Justificativa: a decisão é correta e completa. Inconsistências menores: a tabela fala em esperas "[5ms, 10ms]", mas o teste espera 25 ms; uma exceção lançada pelo próprio `consultar` escapa sem marcar pendência, embora a chave já esteja persistida.
