## Saída bruta

### Hipóteses
- O serviço roda com N réplicas (N máximo conhecido, ex.: 6) atrás de um balanceador; a quota é por cliente/tenant, não por instância.
- Clientes são autenticados (JWT/OAuth); o tenant vem do token validado.
- Existe Redis/Valkey disponível como coordenador. Convenção de erro do projeto: Problem Details (RFC 9457).
- Escopo aqui: o **contrato HTTP** da quota e a política; o limiter em si é implementação (java-construtor).

### Decisões de contrato
1. **Identidade da quota:** tenant/cliente extraído do token autenticado + nome da operação. Nunca de `X-Forwarded-For` ou header livre (burlável, NAT, redes móveis).
2. **Quota global, não por réplica:** o limite vale para o agregado das réplicas, via contador coordenado (Redis/Valkey, janela fixa com script Lua atômico `INCR`+`PEXPIRE`, ou token bucket). Um limiter em memória por réplica daria `N × limite` efetivo e dependeria do roteamento do balanceador.
3. **Estouro da quota = `429 Too Many Requests`** com `Retry-After` (segundos) e corpo `application/problem+json`. É culpa do cliente, não conta no SLO. Opcionalmente `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`.
4. **Saturação do serviço = `503`** com `Retry-After`; não confundir com 429 (503 afeta todos e conta no SLO).
5. **Rejeitar cedo:** a checagem de quota ocorre antes de alocar conexão de banco ou chamada remota; a rejeição deve ser barata.
6. **Falha do coordenador:** nem fail-open (libera tudo) nem fail-closed (derruba o serviço). Usa-se um balde local conservador por réplica. O limite degradado agregado pode chegar a `réplicas máximas × burst local`; dimensione o burst local com o pior N e documente que a decisão local não garante atomicidade global. Métrica `app.ratelimit.falhas_coordenador` sem tags de tenant/chave/IP (cardinalidade fixa).
7. **Algoritmo:** janela fixa admite rajada na fronteira entre janelas; se isso for inaceitável, token bucket (burst limitado, um balde por chave). Escolha conforme o contrato da quota e publique-a.
8. **Clientes que repetem:** retry só dentro do deadline restante; POSTs repetíveis continuam com `Idempotency-Key` (a repetição idempotente não deve consumir quota duas vezes, ou isso deve ser documentado).

### Trecho de contrato (OpenAPI 3.1)
```yaml
responses:
  "429":
    description: Quota do cliente excedida (vale para o conjunto de réplicas).
    headers:
      Retry-After:
        description: Segundos até nova tentativa.
        schema: { type: integer, minimum: 1 }
      RateLimit-Limit:     { schema: { type: integer } }
      RateLimit-Remaining: { schema: { type: integer } }
      RateLimit-Reset:     { schema: { type: integer } }
    content:
      application/problem+json:
        schema: { $ref: "#/components/schemas/ProblemDetail" }
  "503":
    description: Serviço saturado.
    headers:
      Retry-After: { schema: { type: integer, minimum: 1 } }
    content:
      application/problem+json:
        schema: { $ref: "#/components/schemas/ProblemDetail" }
```

### Handler (Java 25 / Spring Boot 4)
```java
@ExceptionHandler(QuotaExcedida.class)
ResponseEntity<ProblemDetail> quota(QuotaExcedida e) {
    var pd = ProblemDetail.forStatusAndDetail(HttpStatus.TOO_MANY_REQUESTS,
        "Limite de requisições excedido.");
    pd.setType(URI.create("https://api.example.com/errors/quota-excedida"));
    return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS)
        .header(HttpHeaders.RETRY_AFTER, String.valueOf(e.segundosAteLiberar()))
        .body(pd);
}
```
`QuotaExcedida` é exceção ilustrativa lançada pela porta de limite. Chave do contador: `ratelimit:{tenant}:{operacao}:{janela}`, tenant vindo do `Authentication`.

### Tabela de status
| Cenário | Status | Header |
|---|---|---|
| Quota do cliente estourou (global entre réplicas) | 429 | Retry-After (+ RateLimit-*) |
| Serviço saturado / admissão rejeitada | 503 | Retry-After |
| Chave de idempotência com payload diferente | 422 (ou 409, um só) | n/a |
| Mesma chave em processamento | 409 | Retry-After curto |

### Testes de contrato (pendentes, não executados)
- Com 2+ instâncias (portas efêmeras) compartilhando o mesmo coordenador, N+1 requisições do mesmo tenant somando as instâncias resultam em 429 com `Retry-After`.
- Tenant ruidoso não afeta outro tenant.
- Fronteira de janela e expiração/rollover.
- Coordenador indisponível: aplica balde local, não responde 500, incrementa a métrica de falhas.
- O `openapi.yaml` carrega (swagger-parser) e declara 429/503 com `Retry-After`.

### Encaminhamentos
- Implementação do limiter (Lua/Redis, token bucket) e do handler: `java-construtor` (ver `spring-data-redis` rate-limiting).
- Quota na borda (gateway/WAF), que não substitui a quota de aplicação: `arquiteto-cloud`.
- Rate limiting de aplicação não protege sozinho contra DDoS de rede.

## Pontuação
- Itens obrigatórios:
  - ✅ Quota local × global: "**Quota global, não por réplica** ... Um limiter em memória por réplica daria `N × limite` efetivo".
  - ✅ Identidade confiável: "tenant/cliente extraído do token autenticado ... Nunca de `X-Forwarded-For` ou header livre".
  - ✅ Operação atômica no coordenador: "janela fixa com script Lua atômico `INCR`+`PEXPIRE`, ou token bucket".
  - ✅ Falha do limitador: "nem fail-open ... nem fail-closed ... balde local conservador ... `réplicas máximas × burst local`" e métrica de falhas.
  - ✅ 429 + `Retry-After`: contrato OpenAPI e handler com `HttpHeaders.RETRY_AFTER`.
  - ✅ Forma de verificar: testes de contrato com 2+ instâncias, tenant ruidoso, rollover e coordenador indisponível.
