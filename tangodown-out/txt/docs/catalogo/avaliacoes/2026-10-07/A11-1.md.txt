### Proporcionalidade: o que NÃO entra (tráfego baixo)

Como o tráfego é baixo, o CRUD fica enxuto. Não entram, por falta de motivo:

- broker (SQS/Kafka), Redis/cache, WebFlux, circuit breaker/Resilience4j, rate limiting, outbox;
- virtual threads configuradas à parte, réplica de leitura, particionamento.

O que **permanece**, porque é barato e evita incidente mesmo com pouco tráfego:

- pool de conexões pequeno e com `connection-timeout` curto;
- paginação com teto de página (ninguém lista a tabela inteira);
- `open-in-view: false`, `ddl-auto: validate` e schema por migration (Flyway);
- erros padronizados (`BusinessException` → 422), validação de bean e limite de tamanho de requisição;
- probes do Actuator (readiness inclui `db`) e graceful shutdown.

```

├── domain/
│   ├── model/Produto.java
│   ├── port/in/        CriarProdutoUseCase, BuscarProdutoUseCase, ListarProdutosUseCase,

│   ├── port/out/       ProdutoRepositoryPort
│   └── exception/      BusinessException, ApplicationException, ProdutoNaoEncontradoException
├── application/usecase/  ProdutoService (implementa as port/in)
└── infrastructure/
    ├── web/            ProdutoController, ProdutoRequest/ProdutoResponse, ApiExceptionHandler
    ├── persistence/    ProdutoEntity, ProdutoJpaRepository, ProdutoRepositoryAdapter, ProdutoMapper
    └── config/         beans dos use cases
```

Regras que valem aqui: `domain` sem `org.springframework.*` nem `jakarta.persistence.*`; o use case injeta a **porta**, nunca o `JpaRepository`; a entidade JPA nunca atravessa o controller (DTO `record` + MapStruct).

### Dependências adicionais sobre o esqueleto (`pom.xml`)

`spring-boot-starter-data-jpa`, `postgresql` (runtime), `mapstruct` 1.6.3 com `mapstruct-processor` em `annotationProcessorPaths`, e Flyway para a migration. Para testes: Testcontainers (PostgreSQL) no perfil `integracao`.

### Código nos trechos relevantes

**Domínio (sem framework)**

```java
// domain/model
public record Produto(Long id, String nome, BigDecimal preco) {
    public Produto {
        // Invariantes no próprio modelo, para o domínio nunca ficar inválido
        if (nome == null || nome.isBlank()) {
            throw new BusinessException("Nome do produto é obrigatório");
        }
        if (preco == null || preco.signum() < 0) {
            throw new BusinessException("Preço não pode ser negativo");
        }
    }

    public Produto comId(Long novoId) {
        return new Produto(novoId, nome, preco);
    }
}

// domain/port/out
public interface ProdutoRepositoryPort {
    Produto salvar(Produto produto);
    Optional<Produto> buscarPorId(Long id);
    List<Produto> listar(int pagina, int tamanho);
    boolean existePorId(Long id);
    void removerPorId(Long id);
}
```

**Caso de uso (a transação mora aqui)**

```java
// application/usecase
public class ProdutoService implements CriarProdutoUseCase, BuscarProdutoUseCase,
        ListarProdutosUseCase, AtualizarProdutoUseCase, RemoverProdutoUseCase {

    private final ProdutoRepositoryPort repositorio;

    public ProdutoService(ProdutoRepositoryPort repositorio) {
        this.repositorio = repositorio;
    }

    @Override
    public Produto criar(String nome, BigDecimal preco) {
        return repositorio.salvar(new Produto(null, nome, preco));
    }

    @Override
    public Produto buscar(Long id) {
        return repositorio.buscarPorId(id).orElseThrow(() -> new ProdutoNaoEncontradoException(id));
    }

    @Override
    public List<Produto> listar(int pagina, int tamanho) {
        return repositorio.listar(pagina, tamanho);
    }

    @Override
    public Produto atualizar(Long id, String nome, BigDecimal preco) {
        if (!repositorio.existePorId(id)) {
            throw new ProdutoNaoEncontradoException(id);
        }
        return repositorio.salvar(new Produto(id, nome, preco));
    }

    @Override
    public void remover(Long id) {
        if (!repositorio.existePorId(id)) {
            throw new ProdutoNaoEncontradoException(id);
        }
        repositorio.removerPorId(id);
    }
}
```

O bean é declarado em `infrastructure/config` (o `ProdutoService` não depende do Spring). Limites do `@Transactional`: operações de escrita simples ficam atômicas no adapter (`save`/`deleteById` já são transacionais); se um caso de uso passar a combinar mais de uma escrita, a transação passa para o use case via bean configurado.

**Persistência (JPA só na infraestrutura)**

```java
// infrastructure/persistence
@Entity
@Table(name = "produtos")
@Getter @Setter @NoArgsConstructor      // nunca @Data em entidade JPA
class ProdutoEntity {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(nullable = false, length = 120)
    private String nome;
    @Column(nullable = false, precision = 12, scale = 2)
    private BigDecimal preco;
    @Version
    private Long versao;               // lock otimista: evita lost-update em PUT concorrente

    @Override
    public boolean equals(Object outro) {   // igualdade só pelo id, segura com proxies
        return outro instanceof ProdutoEntity p && id != null && id.equals(p.id);
    }

    @Override
    public int hashCode() {
        return getClass().hashCode();
    }
}

interface ProdutoJpaRepository extends JpaRepository<ProdutoEntity, Long> { }

@Repository
class ProdutoRepositoryAdapter implements ProdutoRepositoryPort {
    private static final int TAMANHO_MAXIMO = 100;   // teto de página imposto também no adapter
    private final ProdutoJpaRepository jpa;
    private final ProdutoMapper mapper;

    ProdutoRepositoryAdapter(ProdutoJpaRepository jpa, ProdutoMapper mapper) {
        this.jpa = jpa;
        this.mapper = mapper;
    }

    @Override
    public Produto salvar(Produto produto) {
        return mapper.paraDominio(jpa.save(mapper.paraEntidade(produto)));
    }

    @Override
    public List<Produto> listar(int pagina, int tamanho) {
        var pageable = PageRequest.of(pagina, Math.min(tamanho, TAMANHO_MAXIMO), Sort.by("id"));
        return jpa.findAll(pageable).map(mapper::paraDominio).getContent();
    }
    // buscarPorId / existePorId / removerPorId delegam ao jpa + mapper
}
```

## Pontuação
- Itens obrigatórios:
  - ✅ Solução simples (MVC + JPA): variante `rest-crud-banco`; "Não entram, por falta de motivo: broker ..., Redis/cache, WebFlux, circuit breaker".
  - ✅ Paginação: "`max-page-size: 100`", teto também no adapter, e teste "`tamanho=100000` devolve no máximo 100".
  - ⚠️ Timeout: `connection-timeout: 2000` explícito; "tamanho máximo de requisição e timeouts | defaults do esqueleto", sem valor.
  - ❌ Payload: só "limite de tamanho de requisição" e "defaults do esqueleto", sem valor nem mecanismo. O esqueleto limita apenas formulários (`max-http-form-post-size`), não o corpo JSON.
  - ✅ Sem infraestrutura distribuída.
- Falha bloqueadora: não
- Erro técnico: `ProdutoEntity` usa `@Version private Long versao`, e `atualizar` grava `jpa.save(mapper.paraEntidade(new Produto(id, ...)))` com `versao == null`. O Spring Data trata a entidade como nova (versão nula em tipo wrapper), chama `persist` com id preenchido e o PUT falha (entidade destacada passada a persist). A resposta afirma ainda "lock otimista: evita lost-update em PUT concorrente", o que esse fluxo não entrega.
- Justificativa: a proporcionalidade está correta, mas o limite de payload não foi definido, e a operação de atualização, que é parte central do CRUD, quebra pelo uso de `@Version` com `save` de entidade nova. Nota 1.
