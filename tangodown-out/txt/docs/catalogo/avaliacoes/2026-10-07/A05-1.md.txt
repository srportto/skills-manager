## Saída bruta

### Escopo e hipóteses (sem perguntas de volta)

Entendi o pedido como: "o Redis/Valkey (cache) ficou indisponível; faça a aplicação continuar atendendo leitura a partir do banco". Hipóteses declaradas:

- App hexagonal Java 25 / Spring Boot 4, cache-aside em Redis/Valkey, banco PostgreSQL via JPA/HikariCP.
- Operação alvo: leitura por id (`buscarPorId`), dado com staleness tolerável (cacheável). Decisão de negócio crítica (saldo, estoque, pagamento) já consulta a fonte e fica fora disto.
- Pool do banco de 20 conexões por réplica, consulta típica ~20 ms, deadline do cliente 2 s (valores a **medir**; ajustáveis por configuração).
- O código da aplicação está fora do repositório deste catálogo; entrego decisões + trechos, sem gravar nada no repo e sem executar build (não há projeto-alvo), então **nenhuma evidência de execução é alegada**.

### Decisão principal: NÃO enviar "tudo" ao banco

Fazer literalmente o que foi pedido (100% das leituras caindo no banco) é o anti-padrão que `spring-data-redis` descreve: a queda do cache vira queda do banco. O banco não foi dimensionado para o tráfego que o cache absorvia, e todas as conexões do Hikari seriam disputadas, derrubando também escritas e o readiness. Em vez disso, o fallback ao banco é feito de forma **limitada e observável**:

1. Falha do cache nunca falha a requisição: leitura do cache com timeout curto (50–100 ms) e erro tratado como miss.
2. Miss/queda vai ao banco, mas com **limite de concorrência ao banco** (orçamento menor que o pool, reservando conexões para escrita e health), **espera limitada** e **uma única recomputação por chave** (single-flight; chave quente não vira N consultas iguais).
3. Excedente é **rejeitado cedo** com 503 + `Retry-After` (ou serve valor stale, se existir e o contrato permitir) — carga acima da capacidade não é absorvida em fila ilimitada.
4. Deadline: o timeout da consulta é derivado do orçamento restante; sem retry automático em cima do banco já pressionado.
5. Retorno do cache: gravação best-effort (erro ao gravar não falha a leitura); reaquecimento gradual, não todas as chaves de uma vez. TTL com jitter.
6. Observabilidade: taxa de acerto, erros/timeouts do cache, rejeições por limite do banco, recomputações em andamento (queda de acerto + subida de consultas ao banco = sinal de stampede).

Proporcionalidade: sem circuit breaker, broker ou WebFlux; basta limite de concorrência + timeouts + single-flight. Um breaker simples para o *cache* (parar de tentar o Redis por alguns segundos após N falhas) é evolução opcional se a latência do Redis doente aparecer nas métricas.

### Orçamento (conta explícita)

- Pool: 20 conexões/réplica. Reserva: 4 para escrita/health, então **limiteBanco = 16** leituras concorrentes ao banco por réplica.
- Capacidade de leitura ao banco ≈ 16 / 0,020 s = **800 leituras/s por réplica** (Lei de Little). Acima disso, o excedente é rejeitado em até 50 ms de espera, não enfileirado.
- Conexões totais = réplicas máximas × 20 + jobs/admin; conferir contra o orçamento seguro do PostgreSQL (não só `max_connections`).
- Pior caso de uma requisição: leitura do cache 100 ms + espera de vaga 50 ms + consulta 600 ms = 750 ms, dentro dos 2 s do cliente. Sem retry sobre o banco.

Use case com fallback protegido (padrão do `CacheProtegido` do catálogo: single-flight por chave + limite ao banco):

```java
// application/usecase/BuscarProdutoService.java
@Service
public class BuscarProdutoService {

    private final CacheProdutos cache;
    private final ProdutoRepositoryPort repositorio;
    private final Semaphore vagasBanco;              // singleton compartilhado: quota local de leituras ao banco
    private final ConcurrentHashMap<UUID, Boolean> emRecomputacao = new ConcurrentHashMap<>();
    private final Duration esperaPorVaga;
    private final MeterRegistry metricas;

    public BuscarProdutoService(CacheProdutos cache, ProdutoRepositoryPort repositorio,
                                @Qualifier("vagasBanco") Semaphore vagasBanco,
                                Duration esperaPorVaga, MeterRegistry metricas) {
        this.cache = cache;
        this.repositorio = repositorio;
        this.vagasBanco = vagasBanco;
        this.esperaPorVaga = esperaPorVaga;
        this.metricas = metricas;
    }

    public ProdutoResponse buscarPorId(UUID id) {
        var cacheado = lerDoCache(id);
        if (cacheado.isPresent()) {
            metricas.counter("cache.produtos", "resultado", "acerto").increment();
            return cacheado.get();
        }
        metricas.counter("cache.produtos", "resultado", "erro_ou_miss").increment();
        // Chave quente: quem perde a disputa não consulta o banco; é rejeitado e o chamador degrada
        if (emRecomputacao.putIfAbsent(id, Boolean.TRUE) != null) {
            throw new CapacidadeEsgotadaException("Recomputação em andamento", Duration.ofSeconds(1));
        }
        try {
            return carregarDoBancoComLimite(id);
        } finally {
            emRecomputacao.remove(id);
        }
    }

    private Optional<ProdutoResponse> lerDoCache(UUID id) {
        try {
            return cache.obter(id);
        } catch (RuntimeException indisponivel) {
            // Cache fora = miss; nunca propaga a falha do cache para o cliente
            metricas.counter("cache.produtos.falhas").increment();
            return Optional.empty();
        }
    }

    private ProdutoResponse carregarDoBancoComLimite(UUID id) {
        boolean adquiriu;
        try {
            adquiriu = vagasBanco.tryAcquire(esperaPorVaga.toMillis(), TimeUnit.MILLISECONDS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new CapacidadeEsgotadaException("Interrompido", Duration.ofSeconds(1));
        }
        if (!adquiriu) {
            // Rejeição cedo: protege o banco e as conexões reservadas a escrita/health
            metricas.counter("cache.produtos.rejeicoes_banco").increment();
            throw new CapacidadeEsgotadaException("Banco saturado", Duration.ofSeconds(2));
        }
        try {
            var produto = repositorio.buscarResumoPorId(id)               // projeção DTO, readOnly, sem entidade lazy
                    .orElseThrow(() -> new ProdutoNaoEncontradoException(id));
            tentarGuardar(id, produto);
            return produto;
        } finally {
            vagasBanco.release();                                          // sempre devolvida, mesmo em falha
        }
    }

    private void tentarGuardar(UUID id, ProdutoResponse valor) {
        try {
            cache.guardar(id, valor);
        } catch (RuntimeException ignorada) {
            // O valor do banco continua válido sem o cache; não falha a leitura
        }
    }
}
```

Configuração do limite e dos timeouts (valores do orçamento acima):

```java
@Configuration
class LimitesBancoConfig {
    @Bean("vagasBanco")
    Semaphore vagasBanco(@Value("${app.banco.leituras-concorrentes:16}") int limite) {
        return new Semaphore(limite);   // uma instância por JVM; documentar: total = réplicas × 16
    }
}
```

```yaml
spring:
  data.redis:
    timeout: 100ms            # timeout de comando: Redis doente não vira latência da aplicação
    connect-timeout: 100ms
  datasource.hikari:
    maximum-pool-size: 20
    connection-timeout: 500   # espera máxima por conexão
  jpa.properties.jakarta.persistence.query.timeout: 600   # ms, timeout da consulta
app.banco.leituras-concorrentes: 16
```

Mapeamento do erro (adapter de entrada): `CapacidadeEsgotadaException` vira **503** com `Retry-After` e Problem Details (RFC 9457); nunca 500.

Transação: `@Transactional(readOnly = true)` no adapter de leitura (curta, sem I/O externo dentro); leitura e gravação do cache ficam **fora** da transação.

Cache em si: JSON (Jackson 3), nunca serialização JDK; DTO e não entidade; TTL em toda chave com jitter (base + 0 a 10%); aqui o cache-aside é manual para controlar o fallback.

### Provas (escritas antes da implementação; cada uma com o defeito que detecta)

| Defeito detectado | Teste |
|---|---|
| Queda do cache envia mais que o limite de leituras ao banco (esgota o pool) | `naoDeveExcederLimiteDeLeiturasAoBancoComCacheForaDoAr`: cache lança exceção; 40 requisições simultâneas (`CyclicBarrier`); origem presa por `CountDownLatch`; máximo ativo medido com `AtomicInteger` igual a 16; excedentes recebem `CapacidadeEsgotadaException`. `@Timeout(10)`, latches liberados em `finally`. |
| Falha do cache derruba a requisição | `deveAtenderPeloBancoQuandoCacheLancaExcecao`: `obter` lançando; resposta igual ao valor do banco; falha de `guardar` também não propaga. |
| Chave quente gera N consultas idênticas | `chaveQuenteDeveTerUmaUnicaConsultaConcorrenteAoBanco`: 20 chamadas da mesma chave; máximo de consultas concorrentes igual a 1. |
| Vaga vaza após falha do banco | `deveDevolverVagaQuandoBancoFalha`: após exceção, `availablePermits()` volta a 16. |
| Fallback não rejeita no prazo | `deveRejeitarNaEsperaConfiguradaQuandoSaturado` com espera injetada; sem `Thread.sleep` como sincronização. |
| Contrato de erro | `@WebMvcTest`: saturação gera 503 + `Retry-After`; produto inexistente gera 404. |
| Recuperação do cache | Integração (perfil `integracao`, Testcontainers Valkey + Toxiproxy cortando o Redis): derrubar, ver rejeição/limite ativo, restaurar, ver taxa de acerto subir sem pico acima do limite. |

## Pontuação
- Itens obrigatórios:
  - ✅ Limite de concorrência ao banco: "**limiteBanco = 16** leituras concorrentes ao banco por réplica" (`Semaphore` + `tryAcquire` 50 ms), com a conta de Little.
  - ✅ Recomputação única por chave: "**uma única recomputação por chave** (single-flight)", `emRecomputacao.putIfAbsent`.
  - ✅ Rejeição/degradação: "Excedente é **rejeitado cedo** com 503 + `Retry-After` (ou serve valor stale ...)".
  - ✅ Forma de verificar: testes com o defeito que cada um detecta (máximo ativo = 16 com `CyclicBarrier`, chave quente = 1 consulta, vaga devolvida), Toxiproxy e mutação.
- Falha bloqueadora: não
- Justificativa: recusa o fallback irrestrito e entrega single-flight, limite, rejeição, orçamento de tempo e provas. Corrige as lacunas da execução de 2026-10-06.
