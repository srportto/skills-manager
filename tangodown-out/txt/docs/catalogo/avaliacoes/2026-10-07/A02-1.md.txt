# A02 — Execução 1

**Prompt:** Use virtual threads para resolver as 10 conexões disponíveis no banco

**Arquivos do catálogo lidos:** agents/java-construtor.md; skills/resiliencia-controle-fluxo-java/SKILL.md; skills/resiliencia-controle-fluxo-java/references/capacidade-e-limites.md; skills/resiliencia-controle-fluxo-java/references/backpressure-java.md; skills/resiliencia-controle-fluxo-java/references/timeouts-retries-java.md; skills/java-moderno/SKILL.md; skills/java-moderno/references/virtual-threads.md; skills/testes-sistemas-java/references/concorrencia-resiliencia.md (trecho)

## Saída bruta

**Premissa a corrigir: virtual threads não resolvem o limite de 10 conexões.** Elas tornam barata a *espera* por I/O, mas não criam conexões, CPU nem quota. Com 10 conexões no banco, continuam sendo 10 consultas simultâneas. Milhares de virtual threads só deslocam a fila para dentro da JVM, e essa fila é invisível e ilimitada. O que resolve o problema é combinar virtual threads com **admissão limitada** (semáforo/bulkhead), **timeout na aquisição da conexão** e **rejeição explícita do excedente**.

### Hipóteses assumidas (não foram informadas)
- Spring Boot 4 + Java 25, JDBC/JPA com HikariCP, carga I/O-bound (requisições HTTP que consultam o banco).
- As 10 conexões são o orçamento **total** do banco para esta aplicação. Se houver N réplicas, o pool por réplica = 10 / N, menos a reserva para jobs/admin (conexões máximas = réplicas × pool + jobs/admin).
- Deadline de requisição de 2 s; espera máxima por vaga de 200 ms.
- Escopo: nenhum arquivo do repositório foi alterado. Abaixo estão as decisões, o código e as provas a escrever.

### Decisões
| Limite | Unidade | Escopo | Motivo |
|---|---|---|---|
| Pool Hikari `maximum-pool-size` | 8 conexões | por instância | 10 do banco menos 2 reservadas a admin/jobs (ajuste conforme réplicas) |
| `connection-timeout` | 300 ms | aquisição da conexão | não esperar sem limite |
| Semáforo de admissão | 8 permissões, `tryAcquire` 200 ms | por recurso (banco), uma instância por JVM | rejeitar cedo, antes de ocupar a conexão |
| Resposta ao exceder | 503 + `Retry-After` | requisição | saturação, não erro do cliente |
| Retry | nenhum nesta camada | - | efeito pode não ser idempotente; o dono do retry é o chamador |

Alternativa rejeitada: aumentar o pool para "acompanhar" as virtual threads. Isso só move o gargalo para o banco (`max_connections`, CPU, locks). Não retenha a conexão durante backoff ou chamadas remotas: mantenha a transação curta.

### Configuração
```yaml
spring:
  threads:
    virtual:
      enabled: true          # Tomcat e executores do Spring passam a usar virtual threads
  datasource:
    hikari:
      maximum-pool-size: 8
      connection-timeout: 300   # ms; falha rápida em vez de esperar sem fim
```
Mantenha o `public static void main(String[] args)` clássico no entrypoint do Spring Boot.

### Admissão (hexagonal: porta na application, adaptador na infrastructure)
```java
// application: porta que isola a política de admissão do banco
public interface AdmissaoBanco {
    <T> T executar(Supplier<T> trabalho);
}
```
```java
// infrastructure: uma única instância por JVM (um Semaphore por objeto não cria quota global)
@Component
class AdmissaoBancoSemaforo implements AdmissaoBanco {

    private final Semaphore vagas = new Semaphore(8);
    private static final Duration ESPERA_MAXIMA = Duration.ofMillis(200);

    @Override
    public <T> T executar(Supplier<T> trabalho) {
        try {
            // Espera limitada: excedente falha de forma visível, sem fila escondida
            if (!vagas.tryAcquire(ESPERA_MAXIMA.toMillis(), TimeUnit.MILLISECONDS)) {
                throw new BancoSaturadoException(Duration.ofSeconds(1));
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // restaura o flag; não converte em retry
            throw new BancoSaturadoException(Duration.ofSeconds(1));
        }
        try {
            return trabalho.get();
        } finally {
            vagas.release(); // sempre liberado, inclusive em falha
        }
    }
}
```
```java
// Mapeamento para o contrato HTTP (RFC 9457 Problem Details)
@ExceptionHandler(BancoSaturadoException.class)
ResponseEntity<ProblemDetail> saturado(BancoSaturadoException e) {
    var problema = ProblemDetail.forStatusAndDetail(HttpStatus.SERVICE_UNAVAILABLE, "Banco saturado");
    return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)
            .header(HttpHeaders.RETRY_AFTER, String.valueOf(e.retryAfter().toSeconds()))
            .body(problema);
}
```
Uso no caso de uso: `admissao.executar(() -> repositorio.salvar(pedido))`. Para trabalho em lote com concorrência explícita, use uma virtual thread por tarefa (`Executors.newVirtualThreadPerTaskExecutor()`, nunca um pool de virtual threads), deixando o semáforo como limite real:
```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var pedido : pedidos) {
        executor.submit(() -> admissao.executar(() -> repositorio.salvar(pedido)));
    }
}
```

### Observações de Java 25
- Desde o JDK 24 (JEP 491), `synchronized` não prende mais a carrier thread; não é preciso trocar por `ReentrantLock`. Pinning ainda ocorre em código nativo/FFM; detecte com o evento JFR `jdk.VirtualThreadPinned`.
- Evite `ThreadLocal` pesado (multiplica memória com muitas virtual threads); o MDC de log continua válido.
- Observabilidade: métrica de rejeições por saturação e de vagas em uso (cardinalidade fixa).

### Provas (escritas antes da implementação)
1. Máximo ativo nunca passa de 8 com 200 tarefas em virtual threads (largada com `CountDownLatch`, `AtomicInteger` para o máximo).
2. Excedente é rejeitado em até ~200 ms com `BancoSaturadoException`, sem enfileirar.
3. Falha dentro do trabalho libera a vaga (nova admissão funciona depois).
4. Interrupção restaura o flag e não consome vaga.
5. Integração (perfil `integracao`, Testcontainers/PostgreSQL): com pool de 8 e 100 requisições concorrentes, nenhuma excede o `connection-timeout` sem resposta 503.

## Pontuação
- Itens obrigatórios:
  - ✅ Virtual threads não aumentam conexões: "virtual threads não resolvem o limite de 10 conexões ... não criam conexões, CPU nem quota".
  - ✅ Pool ≤ orçamento somado das réplicas: "Se houver N réplicas, o pool por réplica = 10 / N, menos a reserva ... (conexões máximas = réplicas × pool + jobs/admin)"; pool de 8 com 2 reservadas.
  - ✅ Timeout de aquisição: "`connection-timeout` | 300 ms | aquisição da conexão".
  - ✅ Admissão antes do pool: "Semáforo de admissão | 8 permissões, `tryAcquire` 200 ms ... rejeitar cedo, antes de ocupar a conexão" e 503 + `Retry-After`.
  - ✅ Forma de verificar: provas 1–5 (máximo ativo ≤ 8 com latch, rejeição em ~200 ms, liberação em falha, integração com Testcontainers).
- Falha bloqueadora: não
- Justificativa: corrige a premissa e define limites com unidade e escopo, além das provas. Ressalva menor: não diz explicitamente que a admissão deve ocorrer antes de abrir a transação, quando o use case é `@Transactional`.
