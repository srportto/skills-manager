## Saída bruta

No exemplo de checkout já existe um `Timer` chamado `app.requisicoes`, registrado por operação e resultado (`sucesso`, `erro`, `rejeitada`). Ele mede a duração e conta cada requisição lógica a `/pedidos). Mantenha essa métrica agregada: **não** acrescente `traceId`, ID do pedido, cliente ou tenant como tag. Cada valor desses criaria uma série temporal nova e poderia saturar o Prometheus.

Para observabilidade completa, eu faria estes ajustes:

1. **Expor métricas para scrape.** O módulo já tem Actuator, mas o `application.yaml` expõe apenas `health,metrics` e o POM não inclui o registry Prometheus. Adicione ao `integracao/pom.xml`:

   ```xml
   <dependency>
     <groupId>io.micrometer</groupId>
     <artifactId>micrometer-registry-prometheus</artifactId>
   </dependency>
   ```

   E altere a exposição no `application.yaml`:

   ```yaml
   management:
     endpoints:
       web:
         exposure:
           include: health,metrics,prometheus
     metrics:
       distribution:
         percentiles-histogram:
           http.server.requests: true
   ```

   O Actuator fornece `http.server.requests` para a borda HTTP; o histograma permite consultar distribuição de latência. O timer customizado `app.requisicoes` já publica histograma.

2. **Correlacionar cada requisição com trace e logs.** Inclua as dependências gerenciadas pelo Spring Boot para Micrometer Tracing com OpenTelemetry e exportação OTLP:

   ```xml
   <dependency>
     <groupId>io.micrometer</groupId>
     <artifactId>micrometer-tracing-bridge-otel</artifactId>
   </dependency>
   <dependency>
     <groupId>io.opentelemetry</groupId>
     <artifactId>opentelemetry-exporter-otlp</artifactId>
   </dependency>
   ```

   Configure o formato JSON e o envio dos traces ao collector, ajustando o endpoint ao ambiente:

   ```yaml
   logging:
     structured:
       format:
         console: logstash
   management:
     tracing:
       sampling:
         probability: 0.1
     otlp:
       tracing:
         endpoint: http://otel-collector:4318/v1/traces
   ```

   Com Micrometer Tracing ativo, o Spring propaga W3C `traceparent` nas chamadas HTTP instrumentadas e inclui `traceId`/`spanId` no MDC. Assim, os logs JSON de cada requisição ficam correlacionáveis com o trace. A taxa de amostragem deve ser definida considerando tráfego, custo e diagnóstico; não é um valor universal. Se a aplicação não puder usar tracing, um filtro de borda pode gerar ou validar um identificador curto, colocá-lo no MDC e sempre limpar o contexto no `finally`.

3. **Medir o evento de negócio separadamente.** Se “métrica para cada pedido” significa saber quantos pedidos foram realmente criados, adicione um `Counter` como `pedidos.criados` e incremente-o no ponto em que ocorre a criação efetiva. Em operações idempotentes, não incremente novamente ao reproduzir uma resposta já existente. Use apenas tags de conjunto fechado, como uma operação ou resultado conhecido. A métrica de pedidos criados representa eventos de negócio; `app.requisicoes` representa requisições, inclusive erros e rejeições.

4. **Investigar um pedido individual sem cardinalidade explosiva.** Grave o `traceId` e, quando apropriado e sem dados pessoais, o ID do pedido nos logs estruturados e atributos de spans. Use exemplars para saltar de um bucket de latência até um trace de exemplo. Não use esses identificadores em tags, nem crie um segundo ID concorrente quando o tracing já fornece `traceId`.

Depois de instrumentar, valide que `/actuator/prometheus` responde e expõe `http_server_requests`, `app_requisicoes` e o contador de pedidos. Confirme também que um log contém `traceId`, que o collector recebe spans e que requisições repetidas com IDs diferentes não aumentam o número de séries de métricas. Esses resultados ainda precisam ser verificados no ambiente.
