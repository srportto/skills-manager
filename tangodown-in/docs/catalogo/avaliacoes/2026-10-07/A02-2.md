## Saída bruta

### Ponto central: virtual threads não resolvem o limite de 10 conexões

Virtual threads tornam barata a **espera**, mas não criam conexões. Com 10 conexões no banco, a capacidade continua sendo 10 consultas simultâneas. Se eu só ligar virtual threads, milhares de requisições passam a esperar dentro do pool do Hikari, numa fila implícita e sem limite. Isso desloca o gargalo e piora a latência de cauda. O que "resolve" o cenário é a combinação abaixo.

1. Virtual threads, para que a espera pelo I/O não consuma threads do SO.
2. Admissão limitada ao orçamento de conexões, com `Semaphore`/bulkhead e espera máxima curta.
3. Timeout na aquisição de conexão e rejeição visível (503) do excedente.
4. Transações curtas, sem I/O remoto nem backoff dentro da transação.

### Hipóteses assumidas (não houve informação adicional)

- Java 25 e Spring Boot 4 com Tomcat (MVC), JPA/Hibernate e HikariCP. A carga é I/O-bound.
- Orçamento do banco para este serviço: 10 conexões **somadas entre todas as réplicas**. Considero 2 réplicas, então cada uma tem `pool = 5` e 5 permissões. Se for 1 réplica, use 10. Reserve 1 a 2 conexões para jobs, admin e migrations se elas saírem do mesmo orçamento.
- Fluxos de criticidades diferentes (checkout x relatório) disputam o mesmo banco. Reservo permissões para o crítico.
- Espera máxima de admissão: 200 ms. Timeout de aquisição de conexão: 500 ms. Ambos configuráveis.

### Decisões

| Decisão | Valor | Unidade / escopo | Motivo |
|---|---|---|---|
| Virtual threads | `spring.threads.virtual.enabled=true` | por requisição | I/O-bound; elimina pool de threads Tomcat como gargalo |
| Pool Hikari | `maximum-pool-size = 5` por réplica (2 réplicas = 10) | conexões, por instância | A soma das réplicas nunca passa de 10 |
| Admissão (bulkhead) | `Semaphore(5)` por réplica, com 1 permissão reservada ao crítico | permissões, por recurso na JVM | Os 5 slots não podem ser monopolizados por relatório lento |
| Espera na admissão | 200 ms | por requisição | Excedente rejeita cedo, sem fila oculta |
| `connection-timeout` | 500 ms | por aquisição | Rede de segurança caso a admissão e o pool divirjam |
| Rejeição | HTTP 503 + `Retry-After` + métrica | por requisição lógica | Saturação do recurso (429 seria quota do cliente) |
| Executor manual | `newVirtualThreadPerTaskExecutor()`, uma por tarefa, sem pool de virtual threads | por tarefa | O limite é o semáforo, não o executor |

Alternativa rejeitada: aumentar `maximum-pool-size` além do orçamento. Isso estoura `max_connections` do banco com várias réplicas. Também rejeitei confiar só no `connection-timeout` do Hikari. Ele protege, mas não separa o crítico do relatório e deixa milhares de threads esperando.

### Configuração

```yaml
spring:
  threads:
    virtual:
      enabled: true            # Tomcat e executores do Spring passam a usar virtual threads
  datasource:
    hikari:
      maximum-pool-size: 5     # 2 réplicas x 5 = 10 conexões no total

    open-in-view: false        # não segura conexão durante a renderização da resposta

app:
  banco:
    permissoes-total: 5        # igual ao pool desta réplica
    permissoes-reservadas-criticas: 1
    espera-admissao-ms: 200
```

### Código (Java 25)

Pacote `infrastructure`, porque o bulkhead é um detalhe técnico de proteção do recurso. O use case continua sem conhecer semáforo.

```java
package br.com.srportto.app.infrastructure.resiliencia;

import java.time.Duration;
import java.util.concurrent.Callable;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.Semaphore;
import java.util.concurrent.TimeUnit;

public enum Prioridade { CRITICA, NORMAL }

/**
 * Admissão ao banco: limita a concorrência ao orçamento de conexões da réplica.
 * Uma instância por recurso na JVM (a soma entre réplicas não pode passar de 10).
 */
public class BulkheadBanco {

    private final Semaphore total;
    private final Semaphore normais; // normais só podem usar (total - reservadas)
    private final Duration espera;

    public BulkheadBanco(int permissoesTotal, int reservadasCriticas, Duration espera) {
        this.total = new Semaphore(permissoesTotal);
        this.normais = new Semaphore(permissoesTotal - reservadasCriticas);
        this.espera = espera;
    }

    public <T> T executar(Prioridade prioridade, Callable<T> operacao) throws Exception {
        boolean normal = prioridade == Prioridade.NORMAL;
        // Normal passa antes pela cota própria; assim nunca ocupa a reserva do crítico.
        if (normal && !normais.tryAcquire(espera.toMillis(), TimeUnit.MILLISECONDS)) {
            throw new RejectedExecutionException("Banco saturado (fluxo normal)");
        }
        try {
            if (!total.tryAcquire(espera.toMillis(), TimeUnit.MILLISECONDS)) {
                throw new RejectedExecutionException("Banco saturado");
            }
            try {
                return operacao.call();
            } finally {
                total.release(); // liberação em finally, inclusive em falha
            }
        } finally {
            if (normal) {
                normais.release();
            }
        }
    }
}
```

Uso no adapter de entrada. O `@Transactional` continua no use case, e o bulkhead é acionado **antes** de abrir a transação, para não segurar conexão enquanto espera permissão:

```java
@RestController
class PedidoController {

    private final CriarPedidoUseCase criarPedido; // port/in, @Transactional dentro do use case
    private final BulkheadBanco bulkhead;

    PedidoController(CriarPedidoUseCase criarPedido, BulkheadBanco bulkhead) {
        this.criarPedido = criarPedido;
        this.bulkhead = bulkhead;
    }

    @PostMapping("/pedidos")
    ResponseEntity<?> criar(@RequestBody @Valid PedidoRequest request) throws Exception {
        try {
            var pedido = bulkhead.executar(Prioridade.CRITICA, () -> criarPedido.executar(request.paraComando()));
            return ResponseEntity.status(HttpStatus.CREATED).body(PedidoResponse.de(pedido));
        } catch (RejectedExecutionException e) {
            // Rejeição explícita com orientação ao cliente; incrementa métrica de rejeição.
            return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)
                    .header(HttpHeaders.RETRY_AFTER, "1")
                    .build();
        }
    }
}
```

Observações de implementação:

- Nenhuma transação deve conter I/O remoto, e o backoff de retry nunca acontece segurando permissão ou conexão.
- Desde o JDK 24 (JEP 491), `synchronized` não faz pinning da carrier thread. Não é preciso trocar por `ReentrantLock`. Se houver dúvida, meça com o evento JFR `jdk.VirtualThreadPinned`.
- Métricas (Micrometer, cardinalidade fixa): permissões em uso, rejeições por prioridade e tempo de espera por permissão. Hikari já expõe `hikaricp.connections.pending`.

### Provas (escritas antes da implementação)

Teste determinístico com barreira e latch, sem `sleep`, medindo o máximo ativo com `AtomicInteger`:

```java
@Timeout(10)
@Test
void naoDeveExecutarMaisQueAsPermissoesEmParalelo() throws Exception {
    int permissoes = 5, tarefas = 20;
    var bulkhead = new BulkheadBanco(permissoes, 1, Duration.ofMillis(50));
    var ativas = new AtomicInteger();
    var maximo = new AtomicInteger();
    var rejeitadas = new AtomicInteger();
    var largada = new CyclicBarrier(tarefas);
    var liberar = new CountDownLatch(1);

    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        for (int i = 0; i < tarefas; i++) {
            executor.submit(() -> {
                largada.await(5, TimeUnit.SECONDS);
                try {
                    bulkhead.executar(Prioridade.CRITICA, () -> {
                        maximo.accumulateAndGet(ativas.incrementAndGet(), Math::max);
                        try { liberar.await(5, TimeUnit.SECONDS); }
                        finally { ativas.decrementAndGet(); }
                        return null;
                    });
                } catch (RejectedExecutionException e) {
                    rejeitadas.incrementAndGet();
                }
                return null;
            });
        }
        while (rejeitadas.get() < tarefas - permissoes) Thread.onSpinWait();
        liberar.countDown();
    }
    assertEquals(permissoes, maximo.get());
    assertEquals(tarefas - permissoes, rejeitadas.get());
}
```

- `liberaPermissaoMesmoQuandoOperacaoFalha`: depois de uma exceção, as 5 permissões voltam a estar disponíveis.
- `fluxoNormalNaoOcupaReservaDoCritico`: com 4 normais presas, um crítico ainda entra.
- Prova de mutação: remover o `release()` ou a cota `normais` e confirmar que os testes falham.

### Limites e pendências

- Limite: 5 permissões por réplica (1 reservada ao crítico), espera de 200 ms, `connection-timeout` de 500 ms, orçamento total de 10 conexões. A soma entre réplicas vem do banco, não do código. Se o número de réplicas mudar (autoscaling), reajuste `pool` e permissões. Autoscaling sem esse ajuste estoura as 10 conexões.
- Pendência de infraestrutura: confirmar `max_connections` do banco e reservas para outros consumidores. Se o orçamento real for maior, a melhor alavanca é ampliar o orçamento no banco (ou um pooler externo como PgBouncer), não mais threads.
- Pendência: validar com o `java-revisor` em modo `auditoria` antes de declarar pronto (obrigatório pelo meu fluxo).
- Se o gargalo real for consulta lenta e não a quantidade de conexões, o caminho é `especialista-banco-dados` (índices, `EXPLAIN ANALYZE`) e reduzir o tempo de transação.

## Pontuação
- Itens obrigatórios:
  - ✅ Virtual threads não aumentam conexões: "Virtual threads tornam barata a **espera**, mas não criam conexões".
  - ✅ Pool ≤ orçamento somado: "10 conexões **somadas entre todas as réplicas** ... 2 réplicas, então cada uma tem `pool = 5`"; alerta sobre autoscaling.
  - ✅ Timeout de aquisição: "`connection-timeout` | 500 ms | por aquisição".
  - ✅ Admissão antes do pool: "o bulkhead é acionado **antes** de abrir a transação"; `Semaphore(5)` com reserva para o fluxo crítico.
  - ✅ Forma de verificar: teste determinístico com `CyclicBarrier`/latch e `AtomicInteger`, mais mutação e a tabela de comandos.
- Falha bloqueadora: não
- Justificativa: a decisão está correta e contextualizada, com orçamento entre réplicas, limites explícitos e prova executável. Ressalva menor: `enum Prioridade` e `class BulkheadBanco` aparecem como dois tipos públicos no mesmo bloco e precisariam de arquivos separados.
