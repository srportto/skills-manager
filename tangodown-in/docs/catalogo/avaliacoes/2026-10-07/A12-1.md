## Saída bruta

### Interpretação e hipóteses

O pedido pode ser lido de duas formas, e uma delas é perigosa:

- **Literal:** uma métrica Prometheus por pedido, com `traceId` (ou id do pedido) como label. **Não vou fazer assim.** Cada `traceId`/id novo cria uma série temporal nova (cardinalidade ilimitada) e derruba o Prometheus. Regra do catálogo: `traceId` e ids de negócio nunca viram label de métrica.
- **O que provavelmente você quer:** (1) métricas de negócio e RED para o fluxo de pedidos, agregadas, e (2) poder ir de uma métrica a *um pedido/trace concreto*. Isso se resolve com **exemplars** (o Micrometer anexa o `traceId` ao bucket do histograma), **traceId nos logs (MDC)** e **id do pedido como atributo de span**.

Hipóteses: Spring Boot 4 + Micrometer + Actuator já presentes; serviço `PedidoService` com `criar(Pedido)`; Prometheus faz o scrape; existe (ou vamos adicionar) tracing OTel. Resultados possíveis do pedido: `sucesso`, `rejeitado` (validação/saturação), `erro`.

### Decisões

| Necessidade | Onde vai | Por quê |
|---|---|---|
| Quantos pedidos, com que resultado | Counter `pedidos.criados` com label `resultado` (conjunto fechado) | Counter permite `rate()`; rejeição entra no denominador do SLI |
| Latência por pedido | Timer `pedido.processamento` com histograma | p50/p95/p99 e exemplars |
| Pedidos em andamento | Gauge `pedidos.em.processamento` | Saturação (USE) |
| Tentativas à dependência (retry) | Métrica separada | Retry não pode inflar/esconder a taxa de erro da requisição lógica |
| Achar o pedido/trace específico | **Exemplar** + `traceId` no log + tag `pedido.id` no span | Alta cardinalidade só em logs, traces e exemplars |

### 1. Dependências

```xml
<dependency><groupId>io.micrometer</groupId><artifactId>micrometer-registry-prometheus</artifactId></dependency>
<dependency><groupId>io.micrometer</groupId><artifactId>micrometer-tracing-bridge-otel</artifactId></dependency>
<dependency><groupId>io.opentelemetry</groupId><artifactId>opentelemetry-exporter-otlp</artifactId></dependency>
```

### 2. Configuração

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health, info, prometheus, metrics
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
        pedido.processamento: true   # buckets para p95/p99 e exemplars
  tracing:
    sampling:
      probability: 0.1   # decisão de volume/custo; preferir tail sampling no Collector p/ erros e lentidão
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
logging:
  structured:
    format:
      console: logstash   # traceId/spanId do MDC saem como campos do JSON
```

Observação: com o bridge OTel no classpath o Boot coloca `traceId`/`spanId` no MDC sozinho e propaga `traceparent` (W3C). Não crie um segundo identificador concorrente (nada de filtro `X-Trace-Id` próprio nesse cenário; esse filtro só serve para app sem tracing). Para os exemplars aparecerem no scrape, o Prometheus precisa ter exemplar storage habilitado e o scrape ser feito em formato OpenMetrics; confira o nome das propriedades na versão do Boot em uso.

### 3. Instrumentação (Java)

```java
import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import io.micrometer.tracing.Span;
import io.micrometer.tracing.Tracer;
import java.util.concurrent.atomic.AtomicInteger;

@Service
public class PedidoService {

    private static final Logger log = LoggerFactory.getLogger(PedidoService.class);

    private final MeterRegistry registry;
    private final Tracer tracer;
    private final Timer processamento;
    private final AtomicInteger emProcessamento = new AtomicInteger();

    public PedidoService(MeterRegistry registry, Tracer tracer) {
        this.registry = registry;
        this.tracer = tracer;
        this.processamento = Timer.builder("pedido.processamento")
                .description("Latência do processamento de pedido (requisição lógica)")
                .publishPercentileHistogram()
                .register(registry);
        // gauge de saturação: quantos pedidos estão em andamento agora
        registry.gauge("pedidos.em.processamento", emProcessamento);
    }

    public Pedido criar(Pedido pedido) {
        Span span = tracer.nextSpan().name("pedido.criar").start();
        emProcessamento.incrementAndGet();
        String resultado = "erro";
        try (Tracer.SpanInScope ws = tracer.withSpan(span)) {
            // id do pedido: alta cardinalidade -> só no span e no log, NUNCA em label
            span.tag("pedido.id", pedido.id().toString());

            // o Timer roda dentro do span ativo, então o exemplar carrega o traceId
            Pedido criado = processamento.record(() -> salvar(pedido));

            resultado = "sucesso";
            log.info("pedido criado pedidoId={}", criado.id()); // traceId já vem do MDC
            return criado;
        } catch (PedidoInvalidoException | RejeicaoPorSaturacaoException e) {
            resultado = "rejeitado";   // rejeição é resultado e entra no denominador do SLI
            span.error(e);
            throw e;
        } catch (RuntimeException e) {
            span.error(e);
            throw e;
        } finally {
            // label "resultado" tem conjunto fechado: sucesso | rejeitado | erro
            Counter.builder("pedidos.criados")
                    .description("Pedidos por resultado final da requisição lógica")
                    .tag("resultado", resultado)
                    .register(registry)
                    .increment();
            emProcessamento.decrementAndGet();
            span.end();
        }
    }
}
```

Pontos a notar:
- Prometheus converte `pedidos.criados` em `pedidos_criados_total` e `pedido.processamento` em `pedido_processamento_seconds_*`.
- Se houver retry para dependência, conte as tentativas em outra métrica (ex.: `pedido.dependencia.tentativas` com labels `dependencia` e `resultado`), nunca somando na `pedidos.criados`.
- Em rejeições por sobrecarga, logue de forma amostrada/agregada, não uma linha por rejeição.

### 4. Como chegar "no pedido e no traceId" sem label

1. No Grafana, o painel de latência p99 de `pedido_processamento_seconds_bucket` mostra o **exemplar** (ponto) com o `traceId`; clicar abre o trace no backend (Tempo/Jaeger).
2. Com o `traceId`, filtrar os logs JSON (`traceId = ...`) e ver o `pedidoId` da linha de log.
3. No trace, o span `pedido.criar` tem a tag `pedido.id`.

### 5. PromQL dos SLIs

```promql
# taxa por resultado
sum by (resultado) (rate(pedidos_criados_total[5m]))

# taxa de falha (rejeição e erro explícitos no numerador/denominador)
sum(rate(pedidos_criados_total{resultado="erro"}[5m]))
  / sum(rate(pedidos_criados_total[5m]))

# latência p95
histogram_quantile(0.95, sum by (le) (rate(pedido_processamento_seconds_bucket[5m])))

# saturação
max(pedidos_em_processamento)
```

Alertas devem ser por burn rate multi-janela com runbook (não alertar todo erro); posso detalhar depois de definirmos o SLO do pedido.
