### Não vou fazer a liveness falhar quando uma dependência cai

Fazer a liveness falhar em todos os pods quando uma dependência (banco, broker, cache, API externa) cai é o anti-padrão que o catálogo proíbe. O motivo é a semântica das probes:

| Probe | Pergunta | Falha causa |
|---|---|---|
| liveness | O processo está são? (`livenessState`) | **Reinício** do container |
| readiness | Esta réplica pode atender agora? (`readinessState` + dependências necessárias) | Saída do balanceador, sem reinício |

Se a dependência cair e a liveness falhar, o kubelet reinicia **todos os pods ao mesmo tempo**. Isso não conserta a dependência e piora o incidente:
- A aplicação perde capacidade e cada pod passa por uma nova subida da JVM.
- Quando a dependência volta, todos os pods sobem juntos. O pico de conexões pode derrubá-la de novo, e o ciclo se repete (CrashLoopBackOff em cascata).
- Os logs e o estado em memória do momento da falha se perdem, o que dificulta o diagnóstico.

### O que fazer: usar a readiness

O comportamento correto para "dependency down" é **tirar os pods do balanceador, sem reiniciá-los**. Isso se faz colocando a dependência necessária na **readiness**:

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true
      group:
        liveness:
          include: livenessState          # só o processo; nunca banco/broker/cache/API externa
        readiness:
          include: readinessState,db      # só o que é necessário para atender
```

```yaml
# Deployment (trecho)
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30        # cobre a subida da JVM sem initialDelaySeconds grande
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 3
```

Resultado com o banco fora: liveness 200 (nenhum restart), readiness 503 (pods saem do Service) e a recuperação é automática quando a dependência volta. Dependências opcionais ou degradáveis ficam **fora** da readiness. Saturação (fila cheia, CPU) vai para alerta e load shedding, não para probe.

### Se o objetivo era testar o comportamento

Se você queria **simular** a falha, há duas formas seguras:
- **Experimento de chaos** (toxiproxy/Litmus), derrubando a dependência e verificando que a readiness cai e a liveness se mantém. Isso é do agent `engenheiro-chaos`.
- **Teste de integração** (como o `SaudeAplicacaoTest` do catálogo): banco fora, então liveness 200 e readiness 503.

Se você quer forçar o reinício de pods por outro motivo (ex.: processo travado, leak), o caminho é `kubectl rollout restart deployment/<app>` ou corrigir a causa. A liveness deve refletir apenas o travamento do próprio processo.

### Pontos a observar
- Se o `db` na readiness derrubar todas as réplicas por queda do banco, a aplicação fica sem atender (comportamento esperado quando o banco é necessário). Se parte das rotas funciona sem banco, considere degradar em vez de excluir todo o pod.
- Alertas e dashboards da queda da dependência ficam com `especialista-monitoramento`.

### Pendências / hipóteses
- Assumi Spring Boot com Actuator, porta 8080 e prazos de probe ilustrativos; ajuste ao seu tempo real de subida.
- Não validei com `kubectl apply --dry-run=client` porque não alterei manifests nem tenho cluster neste contexto.

## Pontuação
