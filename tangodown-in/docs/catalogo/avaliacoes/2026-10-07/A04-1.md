## Saída bruta

**Não vou parar o `poll()` até o trabalho acabar.** Esse é o anti-padrão que o catálogo reprova. Se o intervalo entre dois `poll()` passar de `max.poll.interval.ms` (padrão 5 min), o membro sai do grupo e ocorre rebalance. As partições vão para outro consumidor, o trabalho em andamento é reprocessado e a lentidão aumenta em cascata. Em vez disso, mantenho o poll vivo e uso **`pause`/`resume`** nas partições ocupadas. Os efeitos de negócio ficam idempotentes e o commit só acontece depois do efeito durável.

### Hipóteses assumidas
- Spring Boot 4 / Java 25, consumidor com `@KafkaListener` ou laço próprio (`KafkaConsumer`).
- O trabalho por registro é lento (I/O, banco ou HTTP), por isso quero processar de forma controlada e não bloquear o poll.
- A ordem por chave importa: uma mensagem por partição por vez.
- O efeito é gravado em banco, com restrição única de idempotência.
- Não conheço os números reais. Medir: tempo por registro (p50/p99), lag e idade do backlog, capacidade do downstream.

### Primeiro: o caso simples (processamento síncrono)
Se cada lote cabe com folga em `max.poll.interval.ms`, não precisa de pausa. Basta reduzir o lote e processar de forma síncrona no listener:

```yaml
spring:
  kafka:
    consumer:
      enable-auto-commit: false
      max-poll-records: 20          # lote x tempo por registro (p99) << max.poll.interval.ms
      properties:
        max.poll.interval.ms: 300000   # não aumente para "esconder" a lentidão
    listener:
      ack-mode: manual
```

```java
@KafkaListener(topics = "pedidos")
void consumir(ConsumerRecord<String, PedidoEvento> registro, Acknowledgment ack) {
    useCase.processar(registro.value().paraComando()); // idempotente, síncrono
    ack.acknowledge();                                 // commit só depois do efeito durável
}
```

Exemplo de conta: 50 ms por registro (p99 200 ms) com `max-poll-records=100` dá cerca de 5 s por lote (pior caso 20 s). Isso está bem abaixo de 5 min.

### Quando o trabalho é lento ou assíncrono: pausa por partição
Padrão do catálogo (`controle-consumo-java.md`):

1. A thread do laço chama `poll()` continuamente, e só ela chama `poll`, `commit` e `pause`. O `KafkaConsumer` não é thread-safe.
2. A partição com trabalho pendente é **pausada**. O próximo `poll()` não traz mais nada dela, então o buffer fica limitado a um lote.
3. Workers (virtual threads) processam **uma mensagem por partição por vez**, com um teto global de trabalho em voo igual à capacidade do downstream (pool de conexões, quota).
4. Os resultados voltam por fila à thread do laço. Ela faz commit de `offset + 1` do concluído e dá `resume` nas partições vazias.
5. Falha transitória: repete a mesma mensagem, com pausa entre tentativas e tentativas limitadas. Esgotadas, vai para o DLT.

```java
// infrastructure/messaging — esboço do laço
while (ativo) {
    var registros = consumer.poll(Duration.ofMillis(200)); // poll nunca para
    for (var r : registros) {
        filaPorParticao.get(new TopicPartition(r.topic(), r.partition())).add(r);
    }
    // pausa partições com trabalho pendente; assim o poll não traz mais delas
    consumer.pause(particoesOcupadas());
    despachar(); // no máximo 1 em voo por partição e limiteEmVoo no total
    // aplica resultados concluídos: commit do offset seguinte ao processado
    var concluidos = resultados.drenar();
    consumer.commitSync(offsetsConcluidos(concluidos));
    consumer.resume(particoesLivres());
}
```

Em `ConsumerRebalanceListener.onPartitionsRevoked`, espere um tempo limitado pelo trabalho em andamento e commite o que concluiu. O restante será reprocessado pelo novo dono, por isso a idempotência é obrigatória. Em `onPartitionsLost`, não commite. O catálogo traz a implementação de referência em `examples/java/integracao/.../ConsumidorKafkaLimitado.java`.

Com spring-kafka puro, o equivalente declarativo é `concurrency` <= número de partições, `max.poll.records` ajustado e `AckMode.MANUAL`. Para pausar quando o downstream sinaliza saturação, use `pause()`/`resume()` do container via `KafkaListenerEndpointRegistry`.

### Erro tratado em um ponto central
Sem `try/catch` no listener decidindo ack. `DefaultErrorHandler` único, com tentativas limitadas e DLT:

```java
@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);  // vai para <topico>.DLT
    var backoff = new ExponentialBackOffWithMaxRetries(3);        // 1 + 3 tentativas, limitado
    backoff.setInitialInterval(1_000L);
    backoff.setMultiplier(2.0);
    backoff.setMaxInterval(10_000L);
    var handler = new DefaultErrorHandler(recoverer, backoff);
    handler.addNotRetryableExceptions(PedidoInvalidoException.class); // permanente: DLT direto
    return handler;
}
```

Atenção: o retry do `DefaultErrorHandler` bloqueia a partição e conta para `max.poll.interval.ms`, então mantenha o backoff curto. Se a publicação no DLT falhar, o offset não é commitado.

### Causa da lentidão
Pausar o poll não resolve a causa. Antes de mexer, meça:
- Lag e idade do backlog por partição, tempo de processamento p50/p99, trabalho em voo, taxa de commit.
- Se o gargalo é o downstream (banco, HTTP): limite a concorrência a ele (admissão com `Semaphore` e timeout de espera) em vez de aumentar consumidores. Dobrar consumidores dobra a pressão no banco.
- O paralelismo máximo é o número de partições. O backlog fica no broker (retenção), não na memória.
- Se o produtor excede a capacidade de forma sustentada, o lag cresce até a retenção. Isso exige mais capacidade do consumo ou agir no produtor.

### Provas que escrevo antes da implementação (TDD)
Todas em Java (JUnit 5, `MockConsumer` para unidade):
1. O poll continua sendo chamado enquanto há partição pausada.
2. Trabalho em voo nunca passa do limite.
3. Commit só do concluído, e a ordem por chave é preservada.
4. DLT indisponível: nada é commitado.
5. Duplicata/reentrega não duplica o efeito (restrição única).
6. Integração (Testcontainers, perfil `integracao`): rebalance e reinício sem efeito duplicado.
