## Saída bruta completa

Para esse escopo, eu começaria com uma aplicação Spring Boot 4 e Java 25, REST MVC com Tomcat e PostgreSQL. A variante adequada é **REST CRUD com banco**, em um único serviço organizado em `domain`, `application` e `infrastructure`. Para tráfego baixo, não há motivo apresentado para adicionar broker, WebFlux, Redis ou circuit breaker.

Como o nome da aplicação e o recurso não foram informados, o exemplo abaixo usa `Produto` apenas como modelo ilustrativo; não representa um projeto gerado pronto para compilar. Defaults aplicáveis: porta 8080, profile `local`, Tomcat e carga baixa. A aplicação também teria `GET /disponibilidade` e probes do Actuator.

A API pode expor:

- `POST /produtos` — criar;
- `GET /produtos/{id}` — consultar;
- `GET /produtos?page=0&size=20` — listar com paginação, limitando `size` a 100;
- `PUT /produtos/{id}` — atualizar com a versão lida pelo cliente;
- `DELETE /produtos/{id}` — excluir.

A separação mínima mantém o domínio independente do Spring e do JPA. O caso de uso depende de uma porta de saída, e o adapter de persistência implementa essa porta:

```java
// domain/model/Produto.java
public record Produto(Long id, String nome, BigDecimal preco, Long versao) {
}

// domain/port/out/ProdutoRepositoryPort.java
public interface ProdutoRepositoryPort {
    Produto salvar(Produto produto);
    Optional<Produto> buscarPorId(Long id);
    List<Produto> listar(int pagina, int tamanho);
    void excluir(Long id);
}

// application/usecase/ListarProdutos.java
@Service
@Transactional(readOnly = true)
public class ListarProdutos {
    private final ProdutoRepositoryPort produtos;

    public ListarProdutos(ProdutoRepositoryPort produtos) {
        this.produtos = produtos;
    }

    public List<Produto> executar(int pagina, int tamanho) {
        int tamanhoLimitado = Math.min(Math.max(tamanho, 1), 100);
        return produtos.listar(Math.max(pagina, 0), tamanhoLimitado);
    }
}
```

Na infraestrutura, a entidade JPA fica separada do record de domínio; o controller recebe e devolve DTOs, nunca a entidade. As gravações ficam em transações curtas nos casos de uso. Para o PUT, usar `@Version` e devolver a nova versão permite detectar atualização concorrente e responder 409. Consultas por ID inexistente podem responder 404.

Configuração inicial proporcional:

- `spring.jpa.open-in-view: false`;
- schema controlado por migrations e `ddl-auto: validate`;
- paginação com tamanho máximo 100; evitar `findAll()` sem `Pageable`;
- pool Hikari pequeno e configurável (por exemplo, até 10 conexões por instância), com timeout de aquisição de 2 segundos; conferir que instâncias × pool cabem no limite do banco;
- endpoint de diagnóstico `dependencias` incluindo o banco, sem colocar o banco na readiness compartilhada;
- credenciais fora do repositório, obtidas por variável de ambiente ou secret manager.

Eu implementaria o CRUD, a validação dos campos e o mapeamento central de erros; depois executaria `mvn clean verify` e o smoke test. Testes de persistência devem usar banco real via Testcontainers no perfil de integração; se o ambiente não tiver Docker, essa evidência fica pendente. Não informo build ou testes como executados nesta resposta.

Esse é um ponto de partida suficiente para CRUD de baixa carga. Pool e limites devem ser revistos se a quantidade de instâncias ou o perfil de consultas mudar.
